# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Durable design decisions

- The product name is **Godemy**.
- No fictional company, no storyline, no recurring characters. Lessons teach directly on the real project the student is building (e.g. the actual Task Tracker CLI), not through dialogue or a workplace narrative. Do not reintroduce a company name, cast, or character illustrations. **Roles are allowed (user decision, 2026-10-12):** a task may arrive as a ticket from a role label — «Тимлид», «Аналитик», «QA» — with a short brief, but never with a name, a company or a running plot (`tests/bootcamp.test.mjs` checks dialogue speakers).
- Persistence: a signed-in user's data (profile, lesson progress, subscription status, quiz answers, lesson feedback, enrollment, practice log) syncs to Postgres via Supabase (`src/lib/cloudSync.js`, table `public.user_state`, migration in `supabase/migrations/`). Sign-in is optional email magic-link, not required to use the platform. `localStorage` remains the fast local cache and the only store for a signed-out visitor — it is not itself the source of truth once a user is signed in.
- Two distinct visual registers currently coexist and should be reconciled, not treated as intentional: the public landing (`/`, `/academy`) uses a dark navy header with a yellow accent; every course cabinet, lesson reader, and trainer uses a light theme (`#eef1fb` background, indigo `#4b3aeb` accent). When touching either surface, prefer converging them rather than deepening the split.
- **Go course structure (user decision, 2026-10-12, order fixed 2026-10-13): bootcamp.** Foundation modules first, then numbered sprints, one sprint = one project = about one working week: Модуль 1 «Старт» → Модуль 2 «Как работают команды» → Модуль 3 «База Go» → Модуль 4 · Спринт 1 «Первый HTTP-сервер» → Модуль 5 · Спринт 2 «Task Tracker CLI» → Модуль 6 · Спринт 3 «Expense Tracker» → Модуль 7 · Спринт 4 «URL Shortener API» → Модуль 8 «Релиз и портфолио». The owner wants the server first: it is the core job task. Numbering is continuous (owner decision, 2026-10-13): every sprint is also a module, so sprint N is module N+3. The label lives in the module's `phase` («МОДУЛЬ 4 · СПРИНТ 1») and is shown above the title on the cabinet card; keep the same numbers in lesson copy and in `public/lessons/course-roadmap.svg`. The old "six modules × five topics × five lessons" rule is cancelled: a module has as many topics and lessons as the job task needs (`src/content/courseCurriculum.js`). Authored now: modules 1–3 and sprints 1–2 — 89 lessons; sprints 3–4 and Релиз still render the generic template and show «В разработке». The full programme is in `docs/go-bootcamp-program.md`. `tests/bootcamp.test.mjs` pins the order.
- **No overlapping material between modules (user feedback, 2026-10-13).** Everything about teams and process lives in module 2: the topic «Продукт и команда» moved there from «Старт», and the short lesson «Agile и Scrum на практике» was removed because the Agile, Kanban and Scrum topics replace it. Before adding a lesson, check that no other module already teaches the same thing; lesson titles must be unique across the course. A lesson that moves between modules keeps its id through the `[title, id]` form in the curriculum, so its text and the learner's completion mark survive.
- Task Tracker's four inner steps are called «этапы», not sprints (UI, `check.go` output «Этап N», page titles): the sprint is the whole project. Data names and URLs (`sprints` in `goCourse.js`, `/go/task-tracker/sprint/N`) are unchanged.
- The owner's course-editor draft in `localStorage` overrides the code curriculum in the owner's own browser. When the structure changes in code, bump `DRAFT_KEY` in `src/content/courseDraft.js` (now v3), otherwise the owner keeps seeing the old course; modules added in code are merged into an existing draft by `withNewModules`.
- Keep `/course-editor` deliberately simple: a module/topic/lesson tree on the left and one focused editing form on the right, gated to a single allowed email via Supabase magic-link auth (`src/components/EditorAuthGate.jsx`). Drafts use `localStorage` as a cache; there is no server-backed draft store yet.
- Lesson authoring uses reorderable blocks: headings, formatted text, images, quotes, lists, dialogue, links, code (language-tagged, with inline `` `code` `` spans parsed in surrounding text), callouts, quizzes, practical tasks with a persisted checklist, and dividers. Preserve a single-column editorial learner preview.
- The public landing (`/`) is the universal Godemy IT-learning entry point; `/academy` is the compact hub for the Go course and trainer. Position Godemy as practice-first: free course and trainer always, subscription unlocks only the certificate.
- `/go/practice` is the Go practice catalogue with search plus filtering by difficulty and topic; task duration shown; opens `/go/practice/:challengeId`.
- SQL is the second Godemy direction: course at `/sql`, practice at `/sql/practice`, exercises at `/sql/practice/:challengeId`. SQL practice runs against a real embedded engine (sql.js) — this is genuine execution, not a string-match check.
- Python is the third direction: course at `/python`, practice at `/python/practice`, exercises at `/python/practice/:challengeId`. Python execution is real (Pyodide in `src/lib/pyodidePlayground.js`, same verify-by-diff scheme as Go: a harness prints results, the learner's output is compared with a reference solution's). Pyodide ships `hashlib` without OpenSSL and `sqlite3` as a separate package; both are loaded at start-up — verify anything new in the real browser, not only with local `python3`.
- Product Management and QA are available directions at `/product` and `/qa`, with practice at `/product/practice` and `/qa/practice`. Product has no practice content yet; QA practice is scenario/checklist-based, not code execution.
- Every course cabinet shares one structure: compact left rail, progress card computed from real completed-lesson counts, a course-specific practice block directly below the progress card, and a module grid. Do not insert an intermediate mini-landing between a course CTA and its cabinet.
- Module cards use a two-part anatomy: an illustration area above the title/meta/progress row. Give modules distinct thin-line compositions per course rather than repeating one generic illustration.
- Certificates belong only to complete course tracks, never to practice catalogues or standalone projects. The certificate catalogue is Go Junior Developer, Python Junior Developer, SQL Junior Developer, Agile, and Scrum; a course with no authored lessons shows as an upcoming programme, never as progress already in motion.
- Achievements and lesson progress are computed from real completion state (`src/lib/progress.js`, `src/lib/achievements.js`), never hardcoded placeholders.
- Cybersecurity is a fully separate course (`/security`, `src/content/security/`, `src/components/SecurityExperience.jsx`); it shares only lesson blocks and `lib/progress.js` with Go and must not require changes to Go. Structure: two short theory modules where every lesson ends with a hands-on task, a trainer of nine "fix the vulnerability" exercises (`/security/practice`), and a four-sprint project (`/security/project`): the learner downloads an intentionally vulnerable stdlib-only app from `public/security-notes/` and closes nine vulnerabilities, verified by the learner running `check.py` locally. All attacks target only the learner's own local training app, never real systems; keep the focus defensive.
- Security project reference solution lives in `examples/security-notes-solution/` and is gitignored so learners cannot find answers in the repo. After changing `app.py` or `check.py`, re-verify: vulnerable version must score 0/9 with the basic-work check OK; a fixed version must score 9/9; sprint-2 fixes alone must give 3/9 and sprint-3 fixes without the log change 8/9. Rebuild the solution by applying the fixes described in the sprints if the local copy is missing.
- Python code blocks in lessons are runnable in place (Pyodide); Go code blocks are runnable only if they are self-contained, with ground-truthed exclusions in `LessonBlocks.jsx` (`NOT_SELF_CONTAINED`).
- Kubernetes и Kafka is a fourth track (`/kubernetes`, content in `src/content/kubernetes/`, driven by the generic `src/components/TrackExperience.jsx` fed a `track` config; Security still uses its own component). It has two short theory modules, a trainer of twelve Pyodide tasks (PyYAML manifest checks, scheduler rules, Kafka partition/group/commit/idempotency models; verified: reference matches, starter doesn't, in real Pyodide) and **no real cluster**. The project "Kafka в kind" is deliberately shown as «в разработке»: no Docker/kind was available to verify it, so never present it as working or add it to the course until it has been run on a real cluster. Trainer copy must say it is a learning model of the rules, not real Kubernetes/Kafka.
- YouTube с нуля is a fifth track (`/youtube`, `src/content/youtube/`, generic `TrackExperience`, no trainer: `practice: null`). Theory is grounded in YouTube's own help/blog pages (links in the last lesson); platform facts such as Partner Program thresholds change, so re-check them against support.google.com before editing. The project "Пять видео" is self-attested via checklists; the platform cannot verify a learner's channel and must say so. Templates live in `public/youtube-kit/`.
- **Core principle (user decision): every course project is real practice done on the learner's own device and verified by a script the learner runs locally** (pattern: `public/security-notes/check.py`, `public/task-tracker/check.go`). Self-attested checklists are acceptable only where nothing can be checked by a machine (e.g. publishing YouTube videos), and must say so.
- Go Task Tracker has a fixed CLI contract (`cliContract`/`contractRules` in `src/content/goCourse.js`: add, list, update, done, delete; `tasks.json` with id/title/done; errors → non-zero exit, no panic; corrupted file not overwritten). `public/task-tracker/check.go` (`//go:build ignore`, only needs Go) checks it per sprint, 26 checks. Reference solution in `examples/task-tracker-solution/` (gitignored). After editing the checker, re-verify: reference 26/26, hello-world project 4/26, naive `len+1`/no-error-handling project 11/26. Lessons must not contradict the contract.
- Python has a local project «Учёт расходов» (`/python/project`, `src/content/python/project.js`, rendered by `TrackProject`; entry card via `project` in `CourseCabinet`). Learner runs `public/python-expenses/check.py` (stdlib only, 27 checks, forces UTF-8 for Windows consoles). Reference in `examples/python-expenses-solution/` (gitignored). Re-verify after edits: reference 27/27, `print("hello")` 1/27, naive argv/float/no-error-handling script 7/27.
- SQL has a local project «Аналитика интернет-магазина» (`/sql/project`, `src/content/sql/project.js`, `TrackProject` + `project` card in `CourseCabinet`). `public/sql-shop/check.py` (stdlib only) builds the learner's `shop.db` (`--make-db`, seed 1), runs a file (`--run`), and checks 12 queries in `queries/` on seed 1 **and** a hidden seed-2 database by result digests — no reference SQL ships. Never edit `public/sql-shop/check.py` by hand: edit `examples/sql-shop-solution/check_template.py` or `queries/*.sql` and run `python3 build_check.py` there (gitignored). Re-verify: reference 12/12; correct alternates (LIKE dates, no ROUND, NOT IN) pass; INNER-JOIN-for-missing, no status filter, values hardcoded from seed 1, ROW_NUMBER instead of RANK and missing ORDER BY all fail.
- QA has a local project «Тестирование интернет-магазина» (`/qa/project`, `src/content/qa/project.js`, `TrackProject` + `project` card). Learner downloads `public/qa-shop/{shop.py,REQUIREMENTS.md,check.py}`, writes `unittest` tests and `bugs.md`. `check.py` runs the tests on the hidden correct module (must pass — no false positives) and on 8 single-bug mutants (each must be caught), plus a structural check of bug reports. Never edit `public/qa-shop/*` by hand: edit `examples/qa-shop-solution/{shop_correct.py,mutants.py,REQUIREMENTS.md,check_template.py}` and run `python3 build.py` there (gitignored). Re-verify: reference tests 9/9; trivial tests 0/9; happy-path-only tests catch 0/8; tests asserting current buggy behaviour fail the correct-version gate.
- Python, SQL and QA have short lesson modules that prepare for their projects (`src/content/{python,sql,qa}/lessons.js`, built by `src/content/lessonTrack.js`, rendered by `TrackLesson` at `/{course}/lesson/...`, listed in the cabinet via `lessons` in `CourseCabinet`; the last lesson leads to the project). Lesson examples must not answer the project tasks. SQL blocks with `run: "shop"` execute in Pyodide on the same shop database the learner builds; `src/lib/shopDbPython.js` is generated from `examples/sql-shop-solution/check_template.py` — regenerate it whenever the generator changes, or lessons and the learner's `shop.db` will diverge. Each runnable block must run on its own (blocks don't share state).
- Kids direction (user decision): courses for schoolchildren teach through **real-life tasks, not games** (pocket money, grades, schedules, vocabulary tests, class journal). Everything runs in the browser — no installation — so the "local check script" principle does not apply to kids' courses; verification is still real (Pyodide verify-by-diff). First course: «Python для школьников» (`/school`, `src/content/school/`, generic `TrackExperience`, 5 lessons + 11 tasks, `project: null`, `projectPlanned: null`). Tone: «ты», short lessons, a runnable example in every lesson, and each lesson's task points to a trainer task by exact title. Verified: every reference passes and every starter fails in real Pyodide.
- Parents' pages for the kids course (`src/components/SchoolPages.jsx`): `/kids` — landing for parents (the main-page card for «Python для школьников» opens it), `/school/report` — progress report computed from real lesson/task completion and practice days (`getCourseDays` in `lib/activity.js`), copyable as text and printable. No fabricated numbers, reviews or prices. Parental consent for under-14 registration is still missing and needs real legal text — do not invent it.
- **Visual direction (user decision, 2026-10-11): light theme with indigo `#4b3aeb` everywhere.** The dark navy/yellow landing register and the sage-green trainer register are legacy; when touching them, move toward the light indigo cabinet style. Primary action = solid indigo button.
- **Tone (user decision, 2026-10-11): address the learner as «ты» everywhere**, including adult courses, trainers, profile and subscription. Rewrite «вы» to «ты» in any copy you touch.
- **Honest volume and money copy.** Count only authored lessons (`courseStats.authoredLessons`, `authoredLessonIds`, `readyModuleIds` in `src/content/courseCurriculum.js`): Go has 89 written lessons and two sprint projects (Bookmarks API in the bootcamp format, Task Tracker in the earlier format); modules without authored lessons show «В разработке» and their lessons are not clickable in the outline. Progress bars and check marks come from real completion only. Money message is one sentence everywhere: lessons, trainers and projects are free; the subscription only unlocks downloading a certificate. Never list courses, trainers, a job-search track or soft-skill content as paid subscription benefits — they are either free or do not exist.
- **Design tokens live in `src/styles-light.css`** (loaded last from `src/main.jsx`): `--g-*` colours, radii, spacing, type scale (`--g-fs-h1`, `--g-fs-h2`, `--g-fs-display`) and the 44px tap target. It also holds the shared light look of the header, footer, landing hero, trainer (`.sql-task-*`, used by every trainer) and code blocks. Write new styles with these tokens; when you touch a legacy rule in another CSS file, move it onto the tokens instead of adding a new hard-coded colour or size. Page `h1` is `--g-fs-h1` everywhere; trainer task titles are smaller on purpose.
- «Ты» is applied across UI, trainers, lessons and projects. Left on «вы» deliberately: legal pages (`LegalPages.jsx`), the owner-only course editor, and the downloadable check scripts in `public/*/check.*` (changing those requires rebuilding and re-verifying each checker). Russian «ты» copy must stay gender-neutral: avoid past-tense and short-adjective forms that need a gender («ты сделал», «ты готов»).
- The landing has one primary action (`Начать с Go`), no name form, and three sections: hero with the three-step "how it works", directions, subscription. Character images (`public/characters/`) were deleted; the profile shows an initial instead of an avatar and only real facts (no hard-coded "last activity" or "member since").
- Code blocks in lessons are syntax-highlighted by `src/lib/highlight.js` (own tokenizer, no dependency: go, python, sql, bash, yaml, json; unknown languages render as plain text). It must never change the code text — `tests/highlight.test.mjs` checks this on every lesson block. Trainer run states are labelled in Russian through `src/lib/runStatus.js`; do not print raw status ids.
- Task Tracker stage page (`SprintPage` in `LearningPages.jsx`, the pre-bootcamp format) order: header with goal and result → task checklist «Что сделать» → «Как понять, что готово» (acceptance criteria + `go run check.go`) → «Если нужна помощь» with collapsed `<details>` blocks (theory, similar example, hints one at a time, self-check, GitHub steps) → finish. Tasks and the check must stay above reference material; do not reintroduce full-height sections for theory. Sprint and setup checklists persist through `lib/taskChecklist.js` (`storageId` prop of `Checklist`), which syncs with the account (`godemy-task-checklist-v1` is in `KNOWN_KEYS`). Never call a storage write inside a React state updater — StrictMode runs updaters twice and the toggle cancels itself.
- **Bootcamp sprint format** (`src/content/goSprints.js`, `src/components/SprintExperience.jsx`, route `/go/sprint/:id/:stage`). A sprint is five steps that repeat a working week: «Задача» (ticket from the role «Тимлид», API contract, acceptance criteria, out of scope) → «Изучи» (theory lessons of the sprint module, documentation links, an "example from a neighbouring team" on another domain) → «Сделай» (repository checklist, a Kanban board of task cards with a WIP limit of 1, the check command) → «Сдай» (repository link) → «Ретро» (three questions saved for the learner, "what you can do now", stack). The methodology behind it is taught earlier, in the module «Как работают команды»; do not use a sprint term in a sprint before that module explains it. Board, submissions and retros are stored by `src/lib/sprintState.js` (`godemy-bootcamp-v1`, in `KNOWN_KEYS`).
- **Submission by GitHub link** (`src/lib/githubCheck.js`, `RepoSubmission.jsx`). The site has no server, so the learner's code is run by GitHub Actions in the learner's own repository: the course ships `check.go` and `godemy-check.yml`, and the site reads the public GitHub API (no token, 60 requests per hour per IP; one sprint check costs two) to confirm the repository is public, both check files are byte-identical to the course files (compared via raw.githubusercontent.com, which can lag up to five minutes) and the latest run of that workflow on the default branch is green. Verified end to end on a real repository with GitHub Actions (green run accepted, red run rejected); to repeat it, push the reference solution to a temporary public repository and make it private right after, because it exposes the answers. Copy must say exactly this and never imply that Godemy runs or reviews the code. The lesson block `submission` uses the lighter check (public repository with at least one commit) at the end of the tools module.
- Sprint «Первый HTTP-сервер»: project Bookmarks API, files in `public/go-sprints/bookmarks-api/` (`check.go`, `//go:build ignore`, needs only Go; 41 checks in six steps that match the six board cards; one check uses the race detector and is skipped where `go build -race` is unavailable). Reference solution in `examples/bookmarks-api-solution/` (gitignored). After editing the checker re-verify: reference 41/41 (also in `docker run golang` on Linux), hello-world 3/41, naive beginner server without validation or mutex 18–19/41, reference with the mutex removed 38/41 every run. Lesson examples use other domains (books, orders, counters) and must not assemble a full CRUD service. Every Go example in the sprint lessons was run locally and in the Go Playground before publishing; `run: false` on a code block marks examples that listen on a port.
- Course content for new modules and sprints is designed with the `course-methodologist` agent (`~/.claude/agents/course-methodologist.md`): programme backwards from job tasks, every fact and link verified, every example run.
